# CLAUDE.md

Заметки для любой Claude-сессии (в том числе коллеги), которая открывает этот репозиторий.
Обновляйте по ходу работы — устаревший файл хуже, чем его отсутствие.

## Правило работы (договорённость с 2026-10-20)

**Перед любыми изменениями в коде сначала задайте все вопросы, которые есть по задаче, и
дождитесь ответов — только потом начинайте что-либо менять.** Не додумывайте неясные
требования молча и не начинайте реализацию «пока ждём ответа». Чтение кода, поиск и
проверки, нужные чтобы сформулировать вопросы, делать можно.

## Что это за проект

«Без Вступительных» — сервис подготовки к перечневым олимпиадам по физике и математике.
Тэглайн: «База вузов — получи своё БВИ в вуз мечты». Подробности продукта и экранов —
в [README.md](README.md).

## Архитектура

- **Фронтенд** — `/src`, Vite + React 18 + TailwindCSS 3, без роутер-библиотеки (свой
  хэш-роутер в [App.jsx](src/App.jsx)), без UI-кита. Данные — через `fetch` к бэкенду, см.
  [src/lib/api.js](src/lib/api.js).
- **Бэкенд** — `/backend`, FastAPI + SQLAlchemy 2.0 (async, asyncpg) + Alembic, БД —
  облачный PostgreSQL на Neon. Подробности — [backend/README.md](backend/README.md).

Раньше это был чисто фронтенд-прототип на захардкоженных данных (`src/data/*.js`). Теперь
контент (разделы/темы/задачи/олимпиады/вузы/тарифы) и прогресс пользователя — в БД, отдаёт их
бэкенд. В `src/data/` остались только презентационные константы без бэкенд-аналога:
`topics.js` — tailwind-классы уровней сложности, `site.js` — маркетинговый копирайт лендинга
и статусные цвета кабинета. **Не добавляйте туда контент заново** — темы каталога и задачи
редактируются в `backend/scripts/seed_data.py`, олимпиады и вузы — в
`backend/scripts/bvi_data.py` (навигатор БВИ), программа и конспекты — в
`backend/scripts/curriculum_*.py` и `theory_*.py` (см. ниже).

## Дизайн — тема «тетрадь и чертёж»

Задача была «сделать дизайн интереснее и непохожим на типичный ИИ-сайт»; договорились не
уходить в яркость, а углубиться в академичность — отсылка к материальной культуре олимпиадной
подготовки (нумерация задач вида §1.1.1, формулы, красная учительская правка), а не generic
EdTech-визуал. Сначала (2026-10-15) тема была сделана только на лендинге как образец, затем
(коммит `3bdcea6`, 2026-10-21) коллега раскатил её **на весь сайт**:

- Палитра `pen` (чернильно-синий, основной) + `mark` (красные чернила правки, акцент) +
  `amber` (уровень «средний», статус «есть вопросы»). Старые `brand`/`clay` в коде больше не
  используются, но ещё объявлены в `tailwind.config.js` — их можно удалить.
- Шрифты: заголовки h1/h2 — Fraunces (`font-serif`), все числа — IBM Plex Mono (`font-mono`),
  остальной текст — Manrope. Подключены одним Google Fonts `<link>` в `index.html`.
- Карточки — плоские листы с волосяной линией, без теней и крупных скруглений; метки
  прямоугольные капителью; у внутренних страниц в шапке линованная бумага (`.grid-paper`).
- Общие куски — классы в [src/index.css](src/index.css) и компоненты в
  [src/components/ui.jsx](src/components/ui.jsx) (`PageHeader`, `Chip`, `Icon`, `Skeleton*`,
  `Link`/`navigate`): вместо надписей «Загружаем…» — скелеты.
- Главная — на моушен-дизайне ([src/components/motion.jsx](src/components/motion.jsx),
  библиотека `framer-motion`): живой чертёж в хиро, заголовок по словам, прочерчиваемое
  подчёркивание, цифры считаются вверх при появлении на экране. Вся анимация выключается
  при системной настройке «уменьшить движение».
- **Цена моушена:** JS-бандл вырос примерно вдвое — с 227 до ~495 КБ (≈150 КБ сжатым).
  Сборку не ломает; если станет важна скорость на мобильном интернете — подгружать
  `framer-motion` только на главной (ленивый импорт).
- Замечено при проверке 2026-10-24: цифры на главной стоят нулями, пока блок не попадёт в
  экран (`CountUp` стартует по `useInView`) — так задумано, это не баг данных.

## Запуск

Бэкенд и фронтенд запускаются раздельно, порядок важен — фронтенд без бэкенда покажет
ошибки загрузки на каждой странице, кроме статичных частей лендинга.

1. Бэкенд: [backend/README.md](backend/README.md) — venv, `.env` со строкой подключения к
   Neon, `alembic upgrade head`, `python -m scripts.seed`, `uvicorn app.main:app --reload
   --port 8000`.
2. Фронтенд: `npm install && npm run dev` в корне (порт 5173, `VITE_API_URL` по умолчанию
   смотрит на `localhost:8000/api`, см. `.env.example`).

### Запуск без доступа к Neon (локальный Postgres)

Строка подключения к Neon есть только у того, кто создавал проект, — `backend/.env` не в
гите. Чтобы поднять всё локально без неё, нужен любой Postgres, SSL выключается переменной:

```
DATABASE_URL=postgresql+asyncpg://postgres@localhost:5433/bvi
DATABASE_SSL=disable
JWT_SECRET=<любая случайная строка>
CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

Дальше как обычно: `alembic upgrade head` → `python -m scripts.seed` → `uvicorn`.

Подводные камни, на которые наткнулись (2026-09-18):
- `DATABASE_SSL` (в `app/config.py`, по умолчанию `require`) добавлен потому, что раньше
  `ssl="require"` был жёстко зашит в `app/database.py` и локальный Postgres без SSL не
  подключался. Для Neon ничего не меняется — просто не задавайте переменную.
- Postgres из pip-пакета `pgserver` (удобен без Docker/админ-прав) **не работает из папки с
  кириллицей в пути** — `initdb` падает с `invalid byte sequence for encoding "UTF8"`.
  Наша папка — `…\Рабочий стол\ии олимпиады`, поэтому бинарники (`pgserver/pginstall`)
  копировали в папку с латинским путём и запускали `initdb --no-locale` / `pg_ctl` оттуда.
  Ещё у этой сборки нет SSL — отсюда и `DATABASE_SSL=disable`.
- Тесты раньше падали при общем прогоне (`pytest` целиком: 2 из 6 с
  `Event loop is closed` / `'NoneType' ... 'send'`), хотя по одному проходили:
  pytest-asyncio даёт каждому тесту новый event loop, а пул соединений engine глобальный.
  Починено автоматической фикстурой в `tests/conftest.py`, которая после каждого теста
  делает `engine.dispose()`. **После обновления кода сначала `alembic upgrade head`
  (сейчас последняя миграция `0013`), потом `python -m scripts.seed`** — иначе сид упадёт на
  отсутствующих таблицах.
- `uvicorn --reload` в этой папке (OneDrive + кириллица в пути) не замечает изменений файлов —
  после правок бэкенда перезапускайте uvicorn руками.

## Прод-деплой (VPS)

Боевой сервер — VPS у sweb.ru (Ubuntu 24.04), поднят вручную 2026-10-10/12,
автодеплой через GitHub Actions настроен 2026-10-15 (см. «Редеплой» ниже).

- **Адрес:** домен **`po-bvi.ru`** (куплен на sweb.ru там же, где VPS; A-записи `@` и `www` →
  IP сервера, DNS — `ns1/ns2.spaceweb.ru`, `ns3/ns4.spaceweb.pro`) и IP `89.111.136.194`
  (поменялся один раз, см. ниже почему). **HTTPS пока нет** — только `http://`.
- **Фронтенд ходит в API по относительному пути `/api`** (переменная `VITE_API_URL=/api` в
  GitHub), то есть на тот же адрес, с которого открыт сайт, — IP, домен или `www`. Поэтому
  CORS на проде не участвует, а смена IP или домена не требует пересборки фронта.
- **Код:** `/home/deploy/PO_BVI` на сервере (не `/root` — см. «Деплой-пользователь»
  ниже), из того же репозитория. Бэкенд в `/home/deploy/PO_BVI/backend/.venv`
  (отдельный venv от БД — на сервере своя локальная БД, не Neon, см. ниже).
- **Фронтенд раздаётся не из `dist/`, а через симлинк `current`** —
  `/home/deploy/PO_BVI/current → releases/<таймстамп>`, nginx `root` смотрит на
  `current`. Каждый деплой кладёт новую сборку в свою папку `releases/<таймстамп>` и
  атомарно переключает симлинк (без момента, когда отдаются наполовину старые/новые
  файлы). Деплой-workflow хранит последние 5 релизов, остальные подчищает.
- **Деплой-пользователь.** Изначально всё (код, бэкенд-процесс) жило под `root` —
  2026-10-15 перенесли на отдельного пользователя `deploy` без пароля (только
  SSH-ключ), с `sudo` ограниченным ровно двумя командами
  (`/etc/sudoers.d/deploy`: `systemctl restart bvi-backend`, `systemctl reload
  nginx`, `NOPASSWD`). Сам `bvi-backend.service` тоже теперь `User=deploy`, не root.
  **Подводный камень при переносе:** venv нельзя просто скопировать/`mv` на новый
  путь — в скриптах (`.venv/bin/uvicorn` и т.п.) зашит абсолютный путь к
  интерпретатору, после переноса папки он бьётся (`systemd` падает с `203/EXEC`).
  Пересоздавать venv (`rm -rf .venv && python3 -m venv .venv && pip install -r
  requirements.txt`) на новом месте.
- **БД:** локальный Postgres на этом же сервере (не Neon!) — пользователь `bvi_user`,
  база `bvi`, слушает только `127.0.0.1:5432` (сознательный выбор — see «Доступ к БД
  только локально» ниже). `backend/.env` на сервере: `DATABASE_SSL=disable`,
  `CORS_ORIGINS=http://89.111.136.194` (на проде роли не играет — запросы с того же адреса).
- **Бэкенд запущен как systemd-сервис** `bvi-backend`
  (`/etc/systemd/system/bvi-backend.service`): `uvicorn app.main:app --host 127.0.0.1
  --port 8000`, `Restart=always`, `enable`d — переживает перезагрузку и падения.
  **Порт 8000 наружу не открыт и не должен быть** — это осознанно, не баг.
- **nginx** (`/etc/nginx/sites-available/bvi`) — единственное, что слушает порт 80
  снаружи: отдаёт статику из `/home/deploy/PO_BVI/current` и проксирует `/api/` на
  `127.0.0.1:8000`. `try_files $uri $uri/ /index.html` — обязателен для SPA
  (хэш-роутинг иначе не работает при прямом заходе на `#/catalog` и т.п.).
- **Доступ к БД только локально** — осознанное решение (а не экономия на настройке):
  Postgres на внешний мир не смотрит, только `bvi-backend` на том же сервере может
  к нему достучаться. Снаружи БД недоступна вообще никак.

### Как выкатить изменения на прод — чек-лист на каждый раз

Код на сервер попадает **только через GitHub**: Deploy собирает то, что лежит в `main` на
GitHub, а не то, что у вас локально. Незапушенные изменения на прод не попадут, даже если
Deploy прошёл зелёным (так уже было 2026-10-20).

**1. Перед коммитом — проверить локально**
- бэкенд: `cd backend && python -m pytest -q` (тесты ходят в ту же dev-базу, что и `.env`);
- фронтенд: `npm run build` — сборка должна пройти без ошибок;
- если менялась схема БД — сначала `python -m alembic upgrade head` на dev-базе, потом
  `python -m scripts.seed`, если менялись данные (порядок важен: сид падает на
  отсутствующих таблицах).

**2. Закоммитить и запушить в `main`**: `git add <файлы>`, `git commit`, `git push`.
Проверить, что пуш прошёл: `git status -sb` → `## main...origin/main` без `[ahead N]`.

**3. Запустить Deploy**: GitHub → **Actions** → **Deploy** → **Run workflow** → ветка `main`
(подробно — в разделе «Редеплой» ниже). Ждать зелёную галочку, ~1–2 минуты.

**4. Сделать то, что Deploy сам не делает** — зависит от того, что менялось:

| Что менялось | Что сделать после Deploy |
| --- | --- |
| Фронтенд (`src/`, `public/`, `index.html`, `tailwind.config.js`) | ничего |
| Код бэкенда (`backend/app/`) | ничего — Deploy делает `git pull` и перезапускает сервис |
| Зависимости (`backend/requirements.txt`, `package.json`) | ничего — Deploy ставит их сам |
| Новая миграция (`backend/alembic/versions/`) | ничего — Deploy запускает `alembic upgrade head` |
| **Контент** (`backend/scripts/*_data.py`, `curriculum_*.py`, `literature_math.py`, `problems_*.py`, даты олимпиад в `bvi_data.py`) | **сид на сервере руками** (команда ниже) |
| **Большие конспекты** (HTML-файлы, их нет в git) | **скопировать папку на сервер и запустить загрузчик** (см. «Большие интерактивные конспекты») |
| Настройки сервера (`backend/.env` на сервере — его нет в git) | поправить файл на сервере и `systemctl restart bvi-backend` |

Сид на сервере (зайти по SSH под root и выполнить от имени `deploy`, чтобы файлы в его
папке не стали принадлежать root):

```
sudo -u deploy bash -c 'cd /home/deploy/PO_BVI/backend && .venv/bin/python -m scripts.seed'
```

В конце сид печатает итог «Засеяно: … тем, … подтем в программе, … ссылок на литературу» —
сверить числа с тем, что получилось локально. Сид безопасен для пользователей: таблицы
`users`, `task_attempts`, `problem_attempts` он не трогает.

**5. Проверить прод**
- открыть `http://po-bvi.ru/` (именно http — HTTPS ещё нет) и сделать hard refresh
  (Ctrl+Shift+R) — иначе браузер может показать старый закэшированный бандл;
- `curl http://po-bvi.ru/api/subjects` → 200;
- пройти руками то, что меняли.

**6. Коллеге — подтянуть изменения локально**: `git pull`, затем на своей dev-базе
`python -m alembic upgrade head` и `python -m scripts.seed`, если в коммите были миграции
или контент. (Пока оба работаем с одной базой Neon, это достаточно сделать одному из нас.)

### Как настроить деплой с нуля (новый сервер или переезд)

Так поднимали текущий сервер 2026-10-10…15. Конфиги ниже — эталон того, что должно
получиться; если чините существующий сервер, сначала сверьте их с файлами на нём.

**1. Сервер.** VPS с Ubuntu 24.04, 2 vCPU / 2 ГБ RAM / 15 ГБ диска хватает с запасом (БД
занимает единицы мегабайт). Зайти под root и поставить пакеты:

```
apt update && apt install -y git nginx postgresql python3-venv python3-pip
```

Проверить, что новый IP не в блок-листе РКН: открыть `http://<ip>/` извне после настройки
nginx (см. «IP уже менялся» ниже — у первого IP была ровно эта проблема).

**2. База.** Postgres слушает только `127.0.0.1` (так в Ubuntu по умолчанию — не открывать
наружу):

```
sudo -u postgres psql -c "CREATE USER bvi_user WITH PASSWORD '<пароль>';"
sudo -u postgres psql -c "CREATE DATABASE bvi OWNER bvi_user;"
```

**3. Пользователь `deploy`** — без пароля, вход только по ключу, `sudo` только на две команды:

```
adduser --disabled-password --gecos "" deploy
chmod o+x /home/deploy          # иначе nginx (www-data) не прочитает статику → 500
```

Файл `/etc/sudoers.d/deploy` (редактировать через `visudo -f /etc/sudoers.d/deploy`,
проверка — `visudo -c`):

```
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart bvi-backend, /usr/bin/systemctl reload nginx
```

**4. Ключ для GitHub Actions → сервер.** На своём компьютере:
`ssh-keygen -t ed25519 -f deploy_key -N ""`. Публичную часть (`deploy_key.pub`) положить
на сервер в `/home/deploy/.ssh/authorized_keys` (владелец `deploy`, права `700` на `.ssh` и
`600` на файл). Приватную — **в base64 одной строкой** (`base64 -w0 deploy_key`) в GitHub →
Settings → Secrets and variables → Actions → **Secrets** → `DEPLOY_SSH_KEY_B64`. После этого
локальные файлы ключа удалить.

**5. Ключ сервер → GitHub (для `git pull`).** Под `deploy` на сервере:

```
ssh-keygen -t ed25519 -f ~/.ssh/github_deploy -N ""
ssh-keyscan -t ed25519 github.com >> ~/.ssh/known_hosts
printf 'Host github.com\n  IdentityFile ~/.ssh/github_deploy\n  IdentitiesOnly yes\n' >> ~/.ssh/config
```

`~/.ssh/github_deploy.pub` добавить в репозиторий: Settings → **Deploy keys** → Add (без
права записи). Без `known_hosts` `git pull` падает с «Host key verification failed».

**6. Код и бэкенд.** Под `deploy`, клонировать **по SSH** (HTTPS к GitHub из сети хостера
не работает):

```
cd ~ && git clone git@github.com:LilFreezyV/Po_BVI.git PO_BVI
cd PO_BVI/backend && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
mkdir -p ~/PO_BVI/releases
```

`backend/.env`:

```
DATABASE_URL=postgresql+asyncpg://bvi_user:<пароль>@127.0.0.1:5432/bvi
DATABASE_SSL=disable
JWT_SECRET=<длинная случайная строка, например из `openssl rand -hex 32`>
CORS_ORIGINS=http://po-bvi.ru
```

Затем `.venv/bin/python -m alembic upgrade head` и `.venv/bin/python -m scripts.seed`.
venv создавать прямо на месте — переносить готовый нельзя (см. «Деплой-пользователь» выше).

**7. systemd** — `/etc/systemd/system/bvi-backend.service`:

```
[Unit]
Description=BVI FastAPI backend
After=network.target postgresql.service

[Service]
User=deploy
WorkingDirectory=/home/deploy/PO_BVI/backend
ExecStart=/home/deploy/PO_BVI/backend/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
Restart=always

[Install]
WantedBy=multi-user.target
```

`systemctl daemon-reload && systemctl enable --now bvi-backend`, проверка —
`curl http://127.0.0.1:8000/api/subjects`. Порт 8000 наружу не открывать.

**8. nginx** — `/etc/nginx/sites-available/bvi`:

```
server {
    listen 80;
    server_name po-bvi.ru www.po-bvi.ru 89.111.136.194;

    root /home/deploy/PO_BVI/current;
    index index.html;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

`ln -s /etc/nginx/sites-available/bvi /etc/nginx/sites-enabled/`, удалить
`sites-enabled/default`, `nginx -t && systemctl reload nginx`. `proxy_pass` — без `/` на
конце: бэкенд сам ждёт префикс `/api`.

**9. GitHub.** Settings → Secrets and variables → Actions:
- **Secrets:** `DEPLOY_SSH_KEY_B64` (шаг 4);
- **Variables:** `VITE_API_URL` = `/api` (во вкладке Variables, не Secrets);
- в `.github/workflows/deploy.yml` поправить `DEPLOY_HOST` на адрес нового сервера и
  запушить.

**10. Первый деплой** — Actions → Deploy → Run workflow. Он соберёт фронт, создаст первый
релиз и симлинк `current`. Проверка — `http://po-bvi.ru/` открывается, данные грузятся.

**11. DNS** — в панели sweb.ru у домена A-записи `@` и `www` на IP сервера. Новый домен
расходится по миру от часа до суток; проверить: `nslookup po-bvi.ru 8.8.8.8`.

**Ещё не сделано:** HTTPS. Когда дойдут руки — `apt install certbot python3-certbot-nginx`,
`certbot --nginx -d po-bvi.ru -d www.po-bvi.ru` (он сам допишет в конфиг nginx `listen 443`
и редирект), после этого в `.env` поменять `CORS_ORIGINS` на `https://…`.

### Сеть хостера блокирует GitHub/npm — это не баг, а особенность окружения

На сервере **не работает `git clone`/`git pull` по HTTPS** и **не работает `npm
install`** — DPI хостера режет TLS-соединения к `github.com` и
`registry.npmjs.org` по SNI (рукопожатие зависает/обрывается). Не пытайтесь это
чинить на уровне сервера — не починится, это сеть, а не конфиг.

Как с этим живём:
- **git по SSH вместо HTTPS работает** — заведён Deploy Key в
  `github.com/LilFreezyV/Po_BVI` → Settings → Deploy keys, на сервере (у `deploy`,
  домашняя папка `/home/deploy/.ssh/`) лежат `github_deploy` + `config` с `Host
  github.com IdentityFile ~/.ssh/github_deploy IdentitiesOnly yes`. `git clone
  git@github.com:...` и `git pull` этим способом работают нормально. (Изначально
  ключ заводили под `root`, при переносе на `deploy` 2026-10-15 скопировали —
  см. «Редеплой» ниже.)
- **`npm install`/`npm run build` на сервере не работают вообще** — фронтенд либо
  собирается **локально** на том компьютере, где ведётся разработка (нужен рабочий
  Node.js) и переносится вручную через `scp`, либо (предпочтительно теперь) —
  собирается на **облачном раннере GitHub Actions** автодеплоем, см. «Редеплой».
  В обоих случаях `dist/` уже содержит `public/problems/*` — Vite сам копирует
  `public/` при сборке, относить отдельно не нужно.
- Права на файлы: домашняя папка пользователя, под которым крутится сайт
  (`/root` или `/home/deploy`), по умолчанию закрыта для чтения не-владельцем, а
  nginx-воркеры работают от `www-data` — без `chmod o+x` на эту папку nginx падает
  с `500`/`Permission denied` на статике, даже если сами файлы читаемые. Проверяйте
  это при любом переносе сайта на новый путь.

### Редеплой — автоматизирован через GitHub Actions (2026-10-15)

`.github/workflows/deploy.yml`, триггер — **вручную**, кнопка «Run workflow» во
вкладке Actions на GitHub (осознанно не на каждый push — оба разработчика коммитят
прямо в `main` без веток, автодеплой любого сырого коммита был бы рискованным).

**Как запустить деплой (инструкция — делать может любой из нас):**
1. Закоммитить и запушить изменения в `main` — workflow забирает код той ветки,
   которую выберете на шаге 2 (обычно `main`).
2. На GitHub открыть репозиторий → вкладка **Actions** → в списке слева workflow
   **Deploy** → справа кнопка **Run workflow** → ветка `main` → зелёная **Run
   workflow**.
3. Открыть запустившийся прогон и следить за шагами: сборка фронта на раннере →
   заливка релиза на сервер → переключение симлинка `current` → `git pull` и
   миграции бэкенда по SSH → рестарт `bvi-backend`/`nginx` → health-check. Весь
   прогон занимает **~1–2 минуты**.
4. Зелёная галочка = выкатилось и health-check прошёл (сайт и `/api/subjects`
   ответили 200). Красный крестик — смотреть лог именно упавшего шага, см. частые
   причины ниже.
5. Нужны права коллаборатора в `github.com/LilFreezyV/Po_BVI` с доступом к Actions
   (у обоих уже есть, ничего дополнительно настраивать не нужно).

Частые причины падения:
- **SSH-шаги не проходят** — протух/не тот ключ `DEPLOY_SSH_KEY_B64` (см.
  «Секреты» ниже) или сервер сменил IP, а переменная/секрет не обновлены (см.
  «IP уже менялся» выше).
- **Health-check красный, остальное прошло** — бэкенд не успел подняться после
  `systemctl restart` за отведённые в workflow несколько секунд, либо упала
  миграция (`alembic upgrade head`). Проверить вручную: `curl
  http://89.111.136.194/api/subjects` — если через несколько секунд уже 200,
  это была ложная тревога по таймингу; если нет — смотреть `journalctl -u
  bvi-backend` на сервере.
- **Задеплоилось, но на сайте старое** — браузер закэшировал старый `index.html`
  или бандл, обычный hard refresh (Ctrl+Shift+R) решает.

Что делает технически: собирает фронтенд на **облачном** раннере GitHub (`npm ci
&& npm run build` с `VITE_API_URL` из репозиторной переменной — у раннера нет
проблем с доступом к npm/GitHub, это их инфраструктура, не наш сервер), заливает
`dist/` по `rsync` в `releases/<таймстамп>` на сервере и атомарно переключает
симлинк `current` → на вкладке «Прод-деплой» выше объяснено зачем. Отдельным шагом
по SSH: `git pull` + `pip install -r requirements.txt` + `alembic upgrade head`
для бэкенда, затем `sudo systemctl restart bvi-backend && sudo systemctl reload
nginx`, в конце health-check (curl на `/api/subjects` и `/`) — если бэкенд не
ответил, джоба падает красным, а не притворяется, что всё ок. Под капотом держит
только последние 5 релизов, старые чистит.

Ходит на сервер **не под root**, а под отдельным `deploy`-пользователем
(`DEPLOY_SSH_KEY_B64` в GitHub Secrets — приватный ключ только у GitHub Actions,
публичный — в `/home/deploy/.ssh/authorized_keys` на сервере) с `sudo`,
ограниченным ровно двумя командами (restart бэкенда, reload nginx) — компрометация
этого ключа не даёт полный доступ к серверу. Секрет называется с суффиксом `_B64`
не просто так: при первой настройке многострочный приватный ключ, вставленный в
поле GitHub Secret как есть, оказался побит (похоже на инъекцию CRLF) — workflow
падал на `error in libcrypto` при попытке его использовать. Починили, закодировав
ключ в base64 в одну строку; workflow декодирует его обратно (`base64 -d`) перед
использованием. Если когда-нибудь понадобится положить в секреты ещё один
многострочный ключ — сразу кодировать в base64, не вставлять как есть.

**Сознательно не автоматизировано:**
- **`python -m scripts.seed` не гоняется автоматически** — пересобирает контент
  (delete+insert), случайно задеплоить правку кода и тем же шагом незаметно
  переписать контент — плохая идея. Если меняли контент — сидите руками отдельно
  через SSH после деплоя.
- **Откат** — пока тоже вручную: `ssh deploy@... "cd /home/deploy/PO_BVI &&
  ln -sfn releases/<предыдущий-таймстамп> current"` + `sudo systemctl reload
  nginx` для отката фронта; для бэкенда — `git checkout <предыдущий коммит>` на
  сервере + restart. Папки `releases/` хранят историю для этого.

## Ключевые решения и почему

- **Пейвол — серверный, не клиентский.** Раньше был чекбокс «Режим подписчика» на фронте
  (чисто декоративный). Теперь `GET /topics/{id}` сам решает, показывать ли текст
  medium/hard-задач, по `topic.free` и `user.subscription_active`. Чекбокс убран
  ([TopicPage.jsx](src/pages/TopicPage.jsx)).
- **Прогресс не хранится агрегатом, а считается на лету** из таблицы `task_attempts`
  (одна строка на пару пользователь+задача) — см. `backend/app/crud/progress.py`. Так нет
  риска рассинхронизации агрегата с реальными попытками.
- **Нет отдельной тестовой БД.** Локально Postgres/Docker нет (проверяли — на машине их
  просто не было), используется один и тот же облачный Neon и для dev, и для тестов
  (`backend/tests/`, смотрят на `.env`).
- **Content-часть бэкенда без своего redeploy-пайплайна.** `scripts/seed_data.py` —
  вручную перенесённые данные из бывших `topics.js`/`site.js`, идемпотентно
  апсертятся `python -m scripts.seed`. Если меняете контент — правьте там, затем
  перезапускайте сид.
- **Обратный отсчёт до «Физтеха» на лендинге — из реальных дат** (2026-10-20). Раньше в карточке
  хиро было захардкожено «74 дня». Теперь отсчёт берёт этапы «Физтеха» из навигатора (с 0012 —
  общая структура этапов всех олимпиад, см. «Даты сезона олимпиад — структурой» ниже): туры и
  финал по физике и математике с полем `starts_at`. Дни считает браузер по московскому
  календарю и пересчитывает раз в минуту; сроки регистрации в отсчёт не идут, только сами туры;
  когда все даты прошли, блок исчезает. Олимпиада для отсчёта задана в `Landing.jsx`
  (`COUNTDOWN_OLYMPIAD = 'fizteh'`). У МФТИ на разных страницах даты финала 2027 расходятся —
  подробности в комментарии к этапам «Физтеха» в `bvi_data.py`. Время финала МФТИ не публиковал,
  поэтому на сайте только дата.
- **Даты сезона олимпиад — структурой, а не текстом** (2026-10-25, миграция `0012`). Решение
  пользователя. Раньше у олимпиады навигатора были текстовые поля «Регистрация / Отбор /
  Финал» и отдельный календарь `bvi_dates` текстом. Теперь у каждой олимпиады список этапов
  (`stages` в [backend/scripts/bvi_data.py](backend/scripts/bvi_data.py), записываются функцией
  `stage(...)`, формат описан в её docstring): вид этапа, даты «с … по …» с точностью до дня
  (`'2026-11-17'`) или месяца (`'2027-02'`), пометка «ориентировочно» (`approx`), время по
  Москве, предмет, примечание, `settled` — «точнее не станет» (например, сроки назначает каждый
  регион). Из этой структуры строится всё: карточки олимпиад на `#/bvi` (подписи дат готовит
  бэкенд — `dates_text`), календарь «Ближайшие даты» (только даты до дня; уже идущие этапы
  сортируются по сроку окончания), обратный отсчёт на главной и напоминания бота. Логика —
  [backend/app/olympiad_dates.py](backend/app/olympiad_dates.py). Общие даты сезона, не
  привязанные к олимпиаде (крайний срок правил приёма), — `GENERAL_DATES` в `app/bvi_meta.py`.
  У олимпиад добавлены `short_title` (короткое имя для календаря и бота) и `dates_url` (какую
  страницу сторожить, по умолчанию `site_url`). 120 этапов перенесены из прежних текстов один в
  один, без новых фактов; «ор.» в тексте стало `approx=True`.
- **Наблюдение за датами олимпиад — бот в общем Telegram-чате** (2026-10-25). Зачем: у 17 из 31
  олимпиады даты ещё ориентировочные, и узнавать о новых датах надо без ручного обхода сайтов.
  Как устроено:
  * Раз в день в 9:00 МСК workflow [.github/workflows/date-watch.yml](.github/workflows/date-watch.yml)
    вызывает на сервере `POST /api/internal/date-watch` (ключ — заголовок `X-Watch-Token`).
    Сервер скачивает страницу с датами каждой олимпиады (`dates_url`), оставляет только строки,
    похожие на даты и этапы, сравнивает со снимком в `date_watch_snapshots` и возвращает готовые
    тексты. Workflow отправляет их в чат. Изменений нет — бот молчит.
  * **Почему так, а не проще:** с VPS Telegram недоступен (DPI хостера, как GitHub и npm —
    проверяли 2026-10-24), а с раннеров GitHub часть российских сайтов олимпиад не открывается.
    Поэтому скачивает сервер, отправляет GitHub. Токен бота хранится только в секретах GitHub.
  * В сообщениях: что появилось и что исчезло на странице, какие страницы перестали открываться
    или снова открываются. По понедельникам — сводка: ориентировочные даты, срок которых
    наступил, недоступные страницы и страницы, где **не нашлось ни одной даты** (сайт рисует
    содержимое скриптом или даты на другой странице — нужна другая ссылка в `dates_url`).
  * **На сайт ничего само не пишется.** Увидели изменение — правите этапы в `bvi_data.py`,
    коммит, Deploy, сид на сервере. Автоматически разбирать даты с чужих сайтов не стали
    сознательно: ошибочный разбор показал бы ученикам неверный дедлайн.
  * Ручка возвращает 404, если ключ на сервере не задан или передан неверный. Сайт пока по
    `http://`, поэтому ключ идёт открытым текстом. Риск небольшой: ключ позволяет только запустить
    проверку фиксированных страниц. После перехода на HTTPS вопрос снимается.
  * Снимки не привязаны к навигатору внешним ключом: сид пересобирает навигатор, а снимки должны
    это переживать. Сменили `dates_url` — первая проверка просто сохранит новый снимок.
  * **Ссылки, поправленные после первого прогона (2026-10-25):** МИФИ (Инженерная, «Росатом»)
    отдавал 404 из-за временного сбоя — ссылки верные, не меняли. ОРМО переехала на
    `info.abiturient.tsu.ru`, даты — на отдельной странице `date-ORMO`. ОМФО: старый адрес на
    МЦНМО оказался заглушкой, настоящий сайт — `физикадлявсех.рф/union-olymp`. У «Газпрома»,
    Открытой олимпиады ИТМО и ведомственных вузов сайты рисуют страницу скриптом, а сайт
    СПб астрономической не отвечает целиком, поэтому у этих четырёх `dates_url` смотрит на их
    страницы в каталоге olimpiada.ru (официальный сайт в карточке остался прежним). Если на
    официальном сайте найдётся страница с датами обычным HTML — лучше переключить на неё.
  * **Два правила против шума**, оба в `date_watch.py`: (1) строки, которые есть сразу на
    нескольких отслеживаемых страницах одного сайта (шапка, лента новостей каталога
    olimpiada.ru), не сравниваются — иначе одна новость каталога дала бы уведомление по каждой
    олимпиаде; (2) живые счётчики «осталось 23 дня», «через 5 часов» вырезаются — иначе
    страница «менялась» бы каждый день. МОШ и «Надежда энергетики» по-прежнему с лентой
    новостей (сотни строк) — настоящие новости там придут уведомлением, это скорее польза.
  * **Найденные при проверке расхождения с нашими данными (не исправлены, ждут решения):**
    у ведомственных вузов olimpiada.ru пишет «Отборочный этап проходит до 11 ноября», а у нас
    «ор. декабрь — январь»; у ОРМО на официальной странице расписания очные даты 7 и 14
    ноября 2026, а у нас «13–22 ноября».
  * **Как подключить** (один раз): создать бота в @BotFather, добавить его в общий чат и написать
    там любое сообщение. Узнать id чата: открыть
    `https://api.telegram.org/bot<токен>/getUpdates` и взять `chat.id` (у групп он
    отрицательный). Придумать ключ (`openssl rand -hex 32`). Положить в GitHub → Settings →
    Secrets and variables → Actions → **Secrets**: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`,
    `DATE_WATCH_TOKEN`. Тот же ключ записать на сервере в `backend/.env` строкой
    `DATE_WATCH_TOKEN=…` и выполнить `systemctl restart bvi-backend`. Проверка — Actions →
    Date watch → Run workflow (галочка «Добавить еженедельную сводку»). Первый прогон пришлёт
    «сохранены первые снимки» и список проблемных страниц.
- **Большие интерактивные конспекты по физике** (начаты 2026-10-31). Тот же формат и тот же
  путь на сайт, что у математики (таблица `conspects`, `subject=physics`, загрузчик
  `load_conspects --subject physics`), но **исходники лежат в git** — папка
  [conspects/](conspects/README.md), а готовые страницы собирает `conspects/build.py` в
  `conspects/dist/` (в `.gitignore`). Почему так: в готовой странице ~0,8 МБ, из которых своего

## На что обратить внимание в этом окружении (Windows)

- На этой машине изначально не было ни Node.js, ни Python-тулинга под бэкенд — оба
  ставили по ходу работы (Node — через `winget install OpenJS.NodeJS.LTS`).
- После установки Node.js уже запущенные процессы (включая сам харнесс Claude Code) не
  видят обновлённый PATH, пока их не перезапустят — приходится вызывать `node`/`npm` по
  полному пути (`C:\Program Files\nodejs\...`) внутри уже открытой сессии.
- В Git Bash на Windows `nohup команда &` не переживает завершение самого bash-вызова —
  для долгоживущих фоновых процессов (`uvicorn`, `vite`) используйте способ, который
  инструмент явно поддерживает как персистентный (в Claude Code — параметр
  `run_in_background` у Bash), а не голый `nohup`.

## Секреты

- `backend/.env` (и локально, и на сервере) — никогда не коммитить, уже в
  `.gitignore`. Локально на машине разработки обычно смотрит на Neon; на сервере —
  на локальный Postgres (`DATABASE_SSL=disable`). `JWT_SECRET` — на каждом
  окружении своё dev-значение, для настоящего продакшена стоит сгенерировать новое
  и не шарить его в чатах/логах.
- **`DEPLOY_SSH_KEY_B64`** (GitHub Secrets, репозиторий Po_BVI) — приватный ключ
  деплой-пользователя `deploy` на сервере, закодированный в base64 одной строкой
  (почему — см. «Редеплой» выше). Публичная часть — в
  `/home/deploy/.ssh/authorized_keys` на VPS. Права ограничены (см. «Прод-деплой»),
  но при компрометации всё равно стоит перевыпустить ключ и обновить его в обоих
  местах.
- `/home/deploy/.ssh/github_deploy` на сервере — **отдельный** ключ, read-only
  Deploy Key в самом репозитории на GitHub (для `git pull` кода бэкенда на сервере).
  Не путать с `DEPLOY_SSH_KEY_B64` выше — разные ключи, разное направление доступа.
- **Наблюдение за датами** (GitHub Secrets): `TELEGRAM_BOT_TOKEN` — токен бота от
  @BotFather, `TELEGRAM_CHAT_ID` — id общего чата, `DATE_WATCH_TOKEN` — ключ к ручке
  проверки. Тот же `DATE_WATCH_TOKEN` лежит на сервере в `backend/.env`; меняете — меняйте в
  обоих местах. Токен бота на сервер не кладётся: в Telegram пишет только GitHub.
